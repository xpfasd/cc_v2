# 广告流程细节

本文基于当前仓库源码整理，范围以 `super-video-downloader-master/super-video-downloader-master/` 为主，额外补充了与其联动的 `Neo-Launcher-main/Neo-Launcher-main/` 中 launcher 插屏场景。

## 1. 先说结论

当前仓库里真正接入并有业务调用的广告形态只有 3 类：

1. `Splash`
2. `Interstitial`
3. `Native`

其中当前能从业务代码确认的场景有：

- 启动页 Splash：`FIRST_SPLASH`、`ACTIVE_SPLASH`
- 首开引导结束插屏：`FIRST_INTERSTITIAL`
- 通用业务插屏：`GENERAL_INTERSTITIAL`
- Launcher 外部应用拉起插屏：`LAUNCHER_APP_INTERSTITIAL`
- 引导页原生广告：`GUIDE_NATIVE`
- 语言页原生广告：`LANGUAGE_NATIVE`
- 首页顶部原生广告：`HOME_TOP_NATIVE`

另外还有几类“代码里定义了，但当前主流程没有实际使用”的能力：

- `TAB_INTERSTITIAL`
- `EXTERNAL_INTERSTITIAL`（和 `LAUNCHER_APP_INTERSTITIAL` 指向同一个 profile 字段）
- `Rewarded`
- `Banner`

## 2. 一个很关键的实现细节

### 2.1 实际场景位来源

当前 `TopOnAdSceneManager` 走的不是 manifest 里那组通用 placement 默认值，而是 `TopOnAdProfiles` 中按 test/prod 切换的硬编码场景位。

- 模式切换来源：`DLApplication -> TopOnAds.initializeFromManifest(...)`
- `initializeFromManifest(...)` 会读取 manifest 里的 `TOPON_TEST_MODE`
- `TopOnAds.initialize(...)` 再调用 `TopOnAdScenes.setTestMode(...)`
- 之后 `TopOnAdSceneManager` 全部通过 `TopOnAdScenes.xxx` 取场景位

也就是说：

- `TOPON_APP_ID` / `TOPON_APP_KEY` 这类 manifest 参数，确实参与 SDK 初始化
- 但具体广告场景位，当前主流程主要还是取 `TopOnAdProfiles.kt` 里写死的各场景 ID

### 2.2 当前默认是测试模式

`gradle.properties` 当前配置：

- `TOPON_TEST_MODE=true`

所以按当前仓库默认构建时，走的是 test profile。

## 4. 启动链路广告

## 4.1 启动 Splash

### 场景

- 首开：`FIRST_SPLASH`
- 非首开：`ACTIVE_SPLASH`

### 预加载时机

`MainActivity.maybeStartLaunchFlow()` 一进启动流就调用：

- `TopOnAdSceneManager.preloadSplash(applicationContext, firstOpen = isFirstStart)`

这里的 `isFirstStart` 来自 `SharedPrefHelper.getIsFirstStart()`，默认值是 `true`。

### 展示时机

不是一进 App 就展示，而是先经历：

1. 启动遮罩出现
2. 启动进度条走满
3. 等待 `SPLASH_DELAY_MS = 30000L`
4. 进入 `continueLaunchFlowAfterSplashDelay()`

然后才尝试 `showSplashIfReady(...)`。

### 关键分支

Splash 不是每次冷启动都一定会展示。

在 `continueLaunchFlowAfterSplashDelay()` 里，代码会先：

1. 预加载首开插屏
2. 预加载引导页 Native
3. 判断是否先拉起 launcher 授权

如果满足：

- 当前不是默认桌面
- `launcherPromptAttempts < 2`

就会直接走 launcher 授权请求并 `return`，这次不会继续执行 `showSplashIfReady(...)`。

这意味着：

- 对“还不是默认桌面”的用户，前两次启动流里，Splash 很可能直接被跳过
- 用户从 launcher 选择页回来后，代码是直接 `showOnboarding()`，不会补放一次 Splash

### 次数 / 频控

- 单次 `MainActivity` 启动流内，最多尝试 1 次
- 没有额外的日频、会话频、冷却时间控制
- 是否首开只影响用哪个 Splash 场景位，不影响是否进入 onboarding

### 失败兜底

`showSplashIfReady(...)` 内部如果：

- `splashAd == null`
- `isReady() == false`
- `show(...)` 返回 `false`
- 或回调收到 `Failed`

都会直接继续后面的 onboarding 流程，不阻塞主链路。

## 4.2 引导页 Native

### 场景

- `GUIDE_NATIVE`

### 预加载时机

`continueLaunchFlowAfterSplashDelay()` 中固定预加载：

- `TopOnAdSceneManager.preloadGuideNative(applicationContext)`

### 展示时机

用户点击 onboarding 第二页的“下一步”时：

- `onboardingPageIndex == 1 && maybeShowGuideNativeAd()`

也就是它不是自动弹，而是卡在第二页到第三页之间。

### 展示方式

- 使用 `onboarding_native_ad_container`
- `fullscreen = true`
- 会把广告放到引导页全屏容器里

### 次数 / 频控

- 单次启动流里最多出现 1 次
- 当前没有额外频控

### 一个容易忽略的细节

引导页 Native 渲染时传的是：

- `renderWhenLoaded = false`

这意味着它**不会在点击后继续等待广告异步加载完成再展示**。

实际效果是：

- 如果这时预加载成果已经拿到了，就展示
- 如果这时还没拿到可渲染广告，就直接跳过广告，进入下一页

所以 `GUIDE_NATIVE` 对“预加载是否赶得上”非常敏感。

## 4.3 首开结束插屏

### 场景

- `FIRST_INTERSTITIAL`

### 预加载时机

仍然是在 `continueLaunchFlowAfterSplashDelay()`：

- `TopOnAdSceneManager.preloadFirstInterstitial(applicationContext)`

### 展示时机

用户在 onboarding 最后一页点击按钮时：

1. 先 `sharedPrefHelper.setIsFirstStart(false)`
2. 再 `TopOnAdSceneManager.showFirstInterstitial(this) { ... }`

### 次数 / 频控

- 逻辑上是“首开流程插屏”
- 单次启动流最多 1 次
- 没有额外频控

### 一个重要细节

`isFirstStart` 是在展示前就被置为 `false` 的。

所以即便这次首开插屏：

- 没准备好
- 展示失败
- 直接走回调

后续启动也已经会按“非首开”处理，不会再继续走 `FIRST_SPLASH`。

### 展示后动作

首开插屏结束后会：

1. `preloadGeneralInterstitial(applicationContext)`
2. `finishLaunchFlow()`

也就是说，它顺手把后续通用插屏库存预热起来了。

## 5. 通用 Interstitial

## 5.1 场景

- `GENERAL_INTERSTITIAL`

## 5.2 预加载策略

它不是应用启动时就全局预加载。

当前能确认的预热来源主要是两类：

1. 首开结束插屏回调里主动 `preloadGeneralInterstitial(...)`
2. 每次 `showGeneralInterstitial(...)` 结束后自动再 preload 一次

`showGeneralInterstitial(...)` 走的是 `showReloadingInterstitial(...)`，因此它属于“展示结束后自动补下一次库存”的模型。

## 5.3 展示点总表

当前主 app 一共能确认 8 个通用插屏展示点：

| 页面 | 触发动作 | 代码行为 |
| --- | --- | --- |
| `WebTabFragment` | 预览网页视频 | 插屏后进入 `VideoPlayerActivity` |
| `WebTabFragment` | 下载网页视频 | 插屏后派发 `downloadVideoEvent` |
| `WebTabFragment` | 浏览器页返回 | 插屏后执行 `webView.goBack()` |
| `ProgressFragment` | 预览解析结果视频 | 插屏后进入 `VideoPlayerActivity` |
| `ProgressFragment` | 下载解析结果视频 | 插屏后派发 `downloadVideoEvent` |
| `VideoFragment` | 删除单个视频 | 插屏后执行删除 |
| `VideoFragment` | 批量删除视频 | 插屏后批量删除并刷新 |
| `VideoFragment` | 播放本地视频 | 插屏后进入 `VideoPlayerActivity` |

## 5.4 次数 / 频控

当前代码里没有看到任何显式频控，例如：

- 每天最多几次
- 每次启动最多几次
- 两次插屏最小间隔
- 某个动作只弹一次

所以目前的真实规则是：

- 这些入口每触发一次，就会尝试展示一次 `GENERAL_INTERSTITIAL`
- 实际次数取决于用户操作次数

## 5.5 失败和补库存逻辑

如果通用插屏：

- 已就绪并正常展示：关闭/失败后会 reload
- 未就绪：会先 `ad.load()`，然后立即放行业务，同时回调里还会再 preload 一次

从代码效果看，`not ready` 这条路径会出现“两次 load 调用叠加到同一个 placement”的情况：

1. `showInterstitial()` 里发现未 ready，先 `ad.load()`
2. 外层 `showReloadingInterstitial()` 的结束回调里又 `preloadInterstitial(...)`

这不会阻塞用户动作，但会造成一次展示失败时的重复 load 尝试。

## 6. Native 广告

## 6.1 语言页 Native

### 场景

- `LANGUAGE_NATIVE`

### 预加载时机

`LanguageSettingsActivity.onCreate()`：

- `preloadNative(applicationContext, TopOnAdScenes.LANGUAGE_NATIVE)`

### 展示时机

- 页面创建后立刻 `post { renderNativeInto(...) }`

### 次数 / 频控

- 每次打开语言页都会尝试 1 次
- 无额外频控

### 特点

这里用的是默认参数：

- `renderWhenLoaded = true`

所以如果 render 当下还没拿到广告，会继续异步 load，等 `Loaded` 后自动回帖重新渲染。

## 6.2 首页顶部 Native

### 场景

- `HOME_TOP_NATIVE`

### 预加载时机

`BrowserHomeFragment.onViewCreated()`：

- `preloadNative(requireContext().applicationContext, TopOnAdScenes.HOME_TOP_NATIVE)`

### 展示时机

- `homeTopNativeAdContainer.post { renderNativeInto(...) }`

### 次数 / 频控

- 每次 Browser Home Fragment 创建时尝试 1 次
- 无额外频控

### 特点

和语言页一样，`renderWhenLoaded = true`，因此允许“先尝试渲染，没加载完就等加载成功后再自动补渲染”。

## 6.3 Native 渲染共性

`TopOnAdSceneManager.renderNativeInto(...)` 的处理逻辑是：

1. 先 `takeLoadedAd()`
2. 没拿到 / handle 无效：先隐藏容器
3. 若 `renderWhenLoaded = true`，继续异步 load，等 `Loaded` 后递归重渲染
4. 若 `renderWhenLoaded = false`，只触发 load，不自动等待本次页面展示
5. 渲染时优先 `renderExpress(...)`
6. 非 express 且 express 失败时，再尝试 `renderStandard(...)`
7. 两种都失败则隐藏容器并销毁 handle

所以当前 3 个 Native 场景的差异重点不在渲染组件，而在 `renderWhenLoaded`：

- `GUIDE_NATIVE`: `false`，赶不上就跳过
- `LANGUAGE_NATIVE`: `true`，可以等加载完成后再补渲染
- `HOME_TOP_NATIVE`: `true`，可以等加载完成后再补渲染

## 7. Neo Launcher 集成插屏

## 7.1 场景

- `LAUNCHER_APP_INTERSTITIAL`

## 7.2 触发时机

发生在 `Neo-Launcher-main/Neo-Launcher-main/src/com/android/launcher3/Launcher.java` 的
`startActivitySafely(...)` 中。

当满足以下条件时会尝试展示：

1. 将要启动的目标包名不是当前 launcher 自己
2. 目标应用不是系统应用

也就是：

- 启动第三方普通 App 时尝试弹
- 启动系统 App 不弹
- 启动自己不弹

## 7.3 展示方式

`Launcher.java` 中直接调用：

- `TopOnAdSceneManager.INSTANCE.showLauncherAppInterstitial(this, () -> { ... })`

广告结束后不会直接马上调 `super.startActivitySafely(...)`，而是先挂起为：

- `mPendingPostInterstitialLaunch`

再等以下条件都满足后真正继续启动：

- `hasBeenResumed()`
- `ACTIVITY_STATE_DEFERRED_RESUMED`
- `ACTIVITY_STATE_WINDOW_FOCUSED`

这是为了避免广告关闭后立刻拉起应用导致 launcher 状态还没恢复好。

## 7.4 预加载现状

当前只在 `TopOnAdSceneManager` 里定义了：

- `preloadLauncherAppInterstitial(context)`

但在当前仓库里没有搜到实际调用点。

所以 launcher 这条链路目前更像是“机会型展示”：

- 如果刚好已有库存，就展示
- 如果没有库存，`showLauncherAppInterstitial(...)` 会立即放行业务，同时开始 load

## 7.5 次数 / 频控

- 代码里没有额外频控
- 每次启动一个符合条件的第三方非系统应用，都会尝试一次

## 8. 已定义但当前未接入主流程的场景

## 8.1 `TAB_INTERSTITIAL`

在 `TopOnAdScenes` 和 `TopOnAdProfiles` 里都有定义，但当前没有搜到实际业务调用。

## 8.2 `EXTERNAL_INTERSTITIAL`

同样有定义，但当前没有看到直接调用入口。

它和 `LAUNCHER_APP_INTERSTITIAL` 共用同一套 `externalInterstitial` profile 字段，本质上像是给不同业务命名预留的别名。

## 8.3 Scenario ID 常量当前没真正传入 SDK

`TopOnAdScenes.kt` 定义了：

- `SCENARIO_FIRST_SPLASH`
- `SCENARIO_ACTIVE_SPLASH`
- `SCENARIO_FIRST_INTERSTITIAL`
- `SCENARIO_GENERAL_INTERSTITIAL`
- `SCENARIO_LAUNCHER_APP_INTERSTITIAL`
- `SCENARIO_GUIDE_NATIVE`
- `SCENARIO_LANGUAGE_NATIVE`
- `SCENARIO_HOME_TOP_NATIVE`

但当前调用链里没有看到把这些 scenarioId 传给 `TopOnAds.show(...)`。

现在的真实行为是：

- 插屏/开屏 `show(...)` 时 `scenarioId` 基本都走默认空字符串
- SDK 被调用的是无 scenario 的 `show(activity)` / `show(activity, container)`

所以这些常量当前更像“语义预留”，不是已生效埋点参数。

## 9. 按页面汇总

### MainActivity 启动流

- 可能涉及：`FIRST_SPLASH` / `ACTIVE_SPLASH` / `GUIDE_NATIVE` / `FIRST_INTERSTITIAL`
- 单次启动流理论上最多看到：
  - 1 次 Splash
  - 1 次 Guide Native
  - 1 次首开插屏
- 但若先走 launcher 授权分支，Splash 会被直接跳过

### BrowserHomeFragment

- `HOME_TOP_NATIVE`

### LanguageSettingsActivity

- `LANGUAGE_NATIVE`

### WebTabFragment

- `GENERAL_INTERSTITIAL`
- 3 个触发点：预览、下载、浏览器返回

### ProgressFragment

- `GENERAL_INTERSTITIAL`
- 2 个触发点：预览、下载

### VideoFragment

- `GENERAL_INTERSTITIAL`
- 3 个触发点：单删、批量删除、播放本地视频

### Neo Launcher

- `LAUNCHER_APP_INTERSTITIAL`
- 触发点：从 launcher 启动第三方非系统应用

## 10. 当前广告次数规则总结

如果只看代码，不看平台后台频控，当前规则可以归纳为：

- Splash：每次启动流最多尝试 1 次
- 引导页 Native：每次启动流最多尝试 1 次
- 首开插屏：首开流程最多 1 次
- 首页顶部 Native：每次首页 Fragment 创建尝试 1 次
- 语言页 Native：每次语言页 Activity 创建尝试 1 次
- 通用插屏：无代码侧频控，按用户动作次数触发
- Launcher 插屏：无代码侧频控，按外部应用拉起次数触发

如果后面要继续细化，最值得补的不是“再找调用点”，而是这几块：

1. 是否需要给 `GENERAL_INTERSTITIAL` 加最小展示间隔
2. `GUIDE_NATIVE` 是否应该允许等待加载完成后再展示
3. `LAUNCHER_APP_INTERSTITIAL` 是否要补真实 preload 时机
4. 是否真的需要把 `scenarioId` 传给 TopOn SDK
