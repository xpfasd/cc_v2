# App 启动链路梳理

## 1. 先说结论

当前版本的真实启动入口已经不是单独的 `SplashActivity`，而是：

1. 系统先拉起 `MainActivity`
2. `MainActivity` 里先显示 Android 12+ 的系统 Splash
3. 然后马上进入 `activity_main.xml` 内部自带的启动遮罩层 `launch_flow_overlay`
4. 遮罩层里依次串起：
   - loading/splash 页
   - 默认桌面授权逻辑
   - onboarding 引导页
   - 启动广告/引导广告/首开插屏
5. 遮罩层结束后，才真正露出首页

所以现在的启动逻辑，本质上是“`MainActivity` 内嵌一整套启动流”。

---

## 2. 入口与初始化

### 2.1 Manifest 入口

`app/src/main/AndroidManifest.xml` 里带 `MAIN + LAUNCHER` 的入口是：

- `com.myAllVideoBrowser.ui.main.home.MainActivity`

也就是说，点桌面图标后，系统直接进 `MainActivity`。

### 2.2 MainActivity 启动时做了什么

`MainActivity.onCreate()` 里的主流程大致是：

1. `installSplashScreen()`
   - 接入 Android 系统启动页。
2. `setContentView(R.layout.activity_main)`
   - 首页 ViewPager、底部 tab、启动遮罩层都在这个布局里。
3. `bindLaunchFlowViews()`
   - 绑定 loading 页、onboarding 页、launcher 授权页、广告容器。
4. 初始化并启动 3 个 ViewModel：
   - `mainViewModel.start()`
   - `proxiesViewModel.start()`
   - `settingsViewModel.start()`
5. 处理外部启动 Intent：
   - `ACTION_VIEW` 时把链接写入 `mainViewModel.openedUrl`
   - `ACTION_SEND` 时把文本写入 `mainViewModel.openedText`
6. 根据是否带 `EXTRA_SKIP_LAUNCH_SPLASH`，决定：
   - 直接续跑引导流
   - 或从冷启动 loading 页开始

### 2.3 首页主体其实已经先初始化了

虽然用户还看不到首页，但 `activity_main.xml` 的主体已经先被创建：

- `ViewPager2`
- 底部 `BottomNavigationView`
- `FragmentContainerView`

只是上面盖了一层全屏 `launch_flow_overlay`。

也就是说，启动页不是单独 Activity，而是首页上面盖了一层全屏引导壳。

---

## 3. 冷启动完整时序

## 3.1 第 0 阶段：系统 Splash

`MainActivity.onCreate()` 一进来就调用 `installSplashScreen()`。

这是系统级 splash，时间很短，主要负责应用刚拉起时的过渡。

## 3.2 第 1 阶段：App 内部 loading 页

`maybeStartLaunchFlow()` 会先执行：

- `showLaunchSurface(launchSplashRoot)`
- `startSplashProgress()`
- `TopOnAdSceneManager.preloadSplash(...)`

这一步会显示 `include_launch_splash.xml` 对应的页面，页面元素包括：

- app logo
- app 名称
- 进度条
- loading 文案

同时会启动一个固定 **3 秒** 的进度动画：

- `SPLASH_DELAY_MS = 3000L`

### 这里同时做的事情

loading 期间会提前做几件事：

1. 预加载 splash 广告
   - `preloadSplash(applicationContext, firstOpen = isFirstStart)`
2. 3 秒结束后再预加载：
   - 首开插屏 `preloadFirstInterstitial(...)`
   - onboarding 原生广告 `preloadGuideNative(...)`

### `isFirstStart` 在这里的作用

`SharedPrefHelper.getIsFirstStart()` 默认是 `true`。

这个标记在启动阶段当前只影响两件事：

1. splash 广告位选首开场景还是常规场景
2. 首页默认书签初始化

**它并不会决定是否展示 onboarding。**

也就是说，从现有代码看，**onboarding 不是“仅首开显示”，而是每次冷启动都会进。**

## 3.3 第 2 阶段：判断是否先拉起“默认桌面授权”

3 秒后会进入这段判断：

- 如果当前 app 还不是默认 Home，并且 `launcherPromptAttempts < 2`
- 就优先发起默认桌面选择
- 否则直接进入 onboarding

判断函数在 `LaunchFlowDecisions.kt`：

- `shouldRequestLauncherBeforeGuide(attempts, isDefaultHome) = !isDefaultHome && attempts < 2`

所以当前策略是：

1. 不是默认桌面时，最多自动拉起 2 次
2. 2 次之后不再强拦，先让用户进首页

## 3.4 第 3 阶段：默认桌面授权流

触发点在 `requestLauncherActivation()`，里面会：

1. `launcherPromptAttempts += 1`
2. `launcherSelectionRequested = true`
3. 调 `requestLauncherSelection(...)`

`requestLauncherSelection(...)` 的逻辑是：

- Android Q 及以上且 `ROLE_HOME` 可用：
  - 走 `RoleManager` 请求默认 Home
- 否则：
  - 跳系统 `Settings.ACTION_HOME_SETTINGS`

### 当前不是先展示自定义授权页，而是直接拉系统授权

虽然 `activity_main.xml` 里包含了 `include_launch_launcher_prompt.xml`，`MainActivity` 里也有：

- `showLauncherPrompt()`
- `maybeShowLauncherPromptOrFinish()`

但从当前代码引用关系看，`maybeShowLauncherPromptOrFinish()` 没有被主链路调用。

也就是说，现阶段真实行为不是：

- loading -> app 内自定义 launcher 授权页 -> 系统授权

而是：

- loading -> 直接发起系统 Home/Launcher 授权

所以这套自定义 launcher prompt UI 更像是“已保留但未接入主流程”的页面。

### 用户授权后的回流

`requestHomeRoleLauncher` 收结果：

- 成功并且 app 已经成为默认 Home：
  - 重新启动 `MainActivity`
  - 带上 `EXTRA_SKIP_LAUNCH_SPLASH = true`
  - 这样会跳过 loading 页，直接继续后续引导
- 取消：
  - 只打日志，不立刻结束流程

### 从系统设置/授权页返回后

`onResume()` 会检查 `launcherSelectionRequested`：

1. 如果还不是默认 Home，且尝试次数还没到 2
   - 再请求一次默认桌面授权
2. 否则
   - 进入 onboarding

所以完整体验是：

- 第一次拒绝/没设成功：可能再弹一次
- 第二次之后：放行到 onboarding 和首页

## 3.5 第 4 阶段：onboarding 引导页

`showOnboarding()` 会：

1. `onboardingPageIndex = 0`
2. `renderOnboardingPage()`
3. `showLaunchSurface(launchOnboardingRoot)`
4. `showLoadedSplashAd()`

这里的 onboarding 一共有 3 页：

1. Download Anytime
2. Easy Download
3. Bookmark Manager

### 一个容易误判的点

`showOnboarding()` 每次冷启动都会走到，只要前面不再卡在 launcher 授权。

当前代码里没有“只首开显示 onboarding”的开关判断。

## 3.6 第 5 阶段：启动广告与引导广告

### 5.6.1 Splash 广告

进入 onboarding 时会先调用：

- `showLoadedSplashAd()`
- `TopOnAdSceneManager.showSplashIfReady(...)`

这意味着：

- splash 广告不是在 loading 页里直接展示
- 而是在切到 onboarding 时，覆盖到 `launch_splash_ad_container` 上展示

如果广告没准备好或展示失败，会直接隐藏广告容器，继续流程。

### 5.6.2 onboarding 第 2 页原生广告

当用户在第 2 页点击 Next 时，代码不是立刻进第 3 页，而是先执行：

- `maybeShowGuideNativeAd()`

这里会把 `TopOnAdScenes.GUIDE_NATIVE` 渲染进全屏容器：

- `onboarding_native_ad_container`

这个广告容器自己可点击，点击后会：

1. 隐藏广告容器
2. `onboardingPageIndex += 1`
3. 进入第 3 页

所以这里的真实链路是：

- 第 2 页 Next
- 先插一个 guide native
- 关掉后才进入第 3 页

### 5.6.3 onboarding 结束后的首开插屏

当用户点到最后一页的 Start：

1. 先 `sharedPrefHelper.setIsFirstStart(false)`
2. 然后 `TopOnAdSceneManager.showFirstInterstitial(...)`
3. 插屏结束后才 `finishLaunchFlow()`

注意：

- `isFirstStart` 是在点击最后一页 Start 时立刻置为 `false`
- 就算插屏没展示成功，也会继续结束启动流

---

## 4. 启动流程里的“授权/权限”到底有哪些

当前真正属于启动链路里的“授权/权限”只有两类。

## 4.1 默认桌面授权

这是启动流里最重的授权动作。

目标是让 app 成为默认 Home/Launcher。

触发时机：

- 冷启动 loading 结束后
- 如果当前不是默认 Home
- 最多自动请求 2 次

失败后的兜底：

- 仍然允许进入 onboarding 和首页
- 但 `finishLaunchFlow()` 后如果还不是默认 Home，会弹一个 Snackbar 提醒

也就是说，启动流对这个授权是“强引导，但不是绝对阻塞”。

## 4.2 Android 13+ 通知权限

启动流结束时 `finishLaunchFlow()` 会调用：

- `maybeRequestNotificationPermission()`

触发条件：

- Android 13 及以上
- `POST_NOTIFICATIONS` 尚未授权
- 本次 Activity 生命周期里还没请求过

它是在：

- splash / onboarding / 首开插屏 都结束后
- 用户即将进入首页时

才弹出来。

## 4.3 不在启动链路里的权限

下面这些权限虽然项目里有，但**不属于启动阶段**：

### 存储/媒体权限

触发位置主要在：

- `WebTabFragment`
- `ProgressFragment`
- `VideoFragment`
- `SettingsFragment`

它们是在下载、访问视频页、修改下载目录时才申请，不在 app 启动时申请。

### Web DRM 权限

`CustomWebChromeClient.onPermissionRequest()` 里会处理 DRM 资源权限，但这是 Web 播放时的行为，不是启动行为。

---

## 5. 从启动结束到首页可用

`finishLaunchFlow()` 做的事情是：

1. 移除启动延迟任务
2. 停掉 splash 进度动画
3. 隐藏整层 `launch_flow_overlay`
4. 隐藏 splash/onboarding/launcher prompt/广告容器
5. 申请通知权限
6. 如果还不是默认 Home，弹出一个 Snackbar 再提醒一次

到这里，首页主体才真正露出来。

### 首页默认落点

默认落在 `MainActivity` 的第 0 个 tab，也就是 Browser/Home 页。

如果是下面这些特殊入口，会在首页出来后进一步处理：

- `ACTION_VIEW`
  - 把传进来的 URL 打开成浏览器标签
- `ACTION_SEND`
  - 把分享过来的文本当成输入，打开成浏览器标签
- 下载完成通知回流
  - 可能切到 Progress 或 Video tab

### 首页露出后还有一个广告位

`BrowserHomeFragment.onViewCreated()` 里会：

1. 预加载 `HOME_TOP_NATIVE`
2. 把原生广告渲染到首页顶部广告容器

所以“看到首页”并不代表广告链路结束，只是启动遮罩结束了。

---

## 6. 当前不在启动链路里的页面

## 6.1 GuideActivity

`GuideActivity` 现在不是启动流程的一部分。

它只是首页 Browser Home 上点 `infoButton` 后手动打开的说明页。

## 6.2 PrivacyPolicyActivity

隐私政策页目前只在设置页里打开，不在启动时弹出，也没有“首次同意”逻辑。

## 6.3 SplashActivity

项目里还保留了旧的 `SplashActivity`：

- 它自己会等 3 秒再跳 `MainActivity`
- 但当前 Manifest 的启动入口不是它

所以它现在更像是遗留页面，不是现网启动主链路。

---

## 7. 广告链路汇总

按启动顺序整理如下：

1. `MainActivity` 冷启动开始
   - 预加载 Splash 广告
2. loading 3 秒结束
   - 预加载首开插屏
   - 预加载 Guide Native
3. 进入 onboarding
   - 展示已准备好的 Splash 广告
4. onboarding 第 2 页点击 Next
   - 展示 Guide Native 全屏原生广告
5. onboarding 最后一页点 Start
   - 展示首开插屏
6. 首页 BrowserHomeFragment 创建后
   - 预加载并展示首页顶部 Native

---

## 8. 配置与状态位汇总

## 8.1 `isFirstStart`

存储位置：

- `SharedPrefHelper`

默认值：

- `true`

当前实际用途：

1. 决定 splash 广告走首开位还是常规位
2. 首页默认书签初始化
3. 在 onboarding 最后一页点 Start 时置为 `false`

**当前并未用它来控制 onboarding 是否显示。**

## 8.2 `launcherPromptAttempts`

存储在 `MainActivity` 内存里，不落盘。

用途：

- 限制默认桌面授权最多自动尝试 2 次

## 8.3 `RETURN_TO_DOWNLOADER_AFTER_HOME_SELECTION`

`LauncherActivationCoordinator` 会把它写成 `true`，`MainActivity` 返回后又清成 `false`。

但从当前代码看，这个标记并没有参与后续判断，属于“有写有清，但没有真正消费”的状态位。

## 9. 现状备注 / 排查时要注意的点

## 9.1 onboarding 现在是“每次冷启动都显示”

这是当前链路里最容易被误以为“仅首开”的地方。

实际上 `isFirstStart` 没有参与 onboarding 显隐判断，所以现在更像“每次冷启动都跑一遍引导层”。

## 9.2 launcher 授权会优先于 onboarding

只要 app 还不是默认 Home，冷启动 loading 后会先拉默认桌面授权，而不是先看引导页。

## 9.3 默认桌面授权失败并不会挡死首页

最多自动拉 2 次。

2 次之后仍然会放用户进入 onboarding 和首页，只是在首页再给一次 Snackbar 提醒。

## 9.4 `SplashActivity` 是遗留链路

如果后续排查“为什么有两个 splash 实现”，要以 `MainActivity + launch_flow_overlay` 为准，不要误把 `SplashActivity` 当成现行主入口。

## 9.5 自定义 launcher prompt 页面目前像遗留/未接通代码

`include_launch_launcher_prompt.xml` 和对应点击逻辑仍然在，但主启动链路当前是直接请求系统授权，没有先展示这层自定义页面。

排查 launcher 启动体验时，要区分：

- 当前真实在走的：系统 Home 授权 / 系统 Home 设置页
- 当前代码里留着但未真正走到的：app 自己的 launcher prompt 页面

## 9.6 `DLApplication` 需要额外核对

代码里有 `DLApplication`，负责：

- TopOn 初始化
- WorkManager 初始化
- YoutubeDL 初始化/更新
- 代理服务启动

但当前我看到的合并后 Manifest `<application>` 节点没有显式 `android:name`。

这意味着这里还需要再确认一次：

- 是不是还有别的构建产物/渠道 manifest 会补上
- 还是当前配置确实漏配了 Application

如果这里漏配，理论上会影响 Dagger/广告/WorkManager/启动初始化链路。
